# SENTINEL submission video: recording procedure

Recommended length: 3 minutes, plus an optional 45-second comparison. Adjust to your competition's actual time limit.

## Files

- Upload `01_UPLOAD_SENTINEL_TEST.txt` for the main demonstration.
- Upload `02_OPTIONAL_REVISED_PLAN.txt` ONLY in a separate, fresh audit for the optional comparison.
- `EXPECTED_RESULTS.json` is the answer key for you. Do NOT upload it, this guide, or the ZIP: doing so changes the input and invalidates the expected counts.
- Both project files contain synthetic, fictional material. Present them as a controlled demonstration, not a real customer case or an independent accuracy benchmark.

## Before recording

1. Start SENTINEL with the local launcher if needed. Open http://127.0.0.1:4173/.
2. Export any work you need to keep, then reload the page. Reloading clears input files and review state.
3. Use a large browser window and readable zoom. Close unrelated tabs and silence notifications.
4. Keep the test file in an easy-to-find folder. Rehearse the entire sequence once.
5. Start a screen recording with microphone audio. Record the actual interaction; do not imply that prewritten outcomes were generated by a language model.

2. Enter `CampusDesk revised plan` as Project Name.
3. Upload ONLY `02_OPTIONAL_REVISED_PLAN.txt`; keep the paste box empty.
4. Click **Run project audit**.
5. Show **0 review candidates** and **Mention found** for all eight coverage dimensions.
6. Say: “The revised plan reconciles the dates and budgets, assigns owners, and documents controls recognized by the engine. The candidates disappear. Zero detected findings does not prove the project is safe, and documented controls still need implementation evidence.”

Do not upload the original and revised plan together. The current engine does not understand document supersession; combining them can preserve conflicts or let later control mentions affect the earlier document's coverage.

## Pass/fail rehearsal checklist

- [ ] Primary text file appears in the uploaded file list.
- [ ] Audit returns exactly 12 candidates without a thin-input notice.
- [ ] All eight dimensions show Review needed.
- [ ] Type filters show A: 1, B: 1, C: 8, D: 2.
- [ ] Source viewer shows the original filename, line number, and quote.
- [ ] F-11 ratings 4/4/4/5/2 give 160, HIGH.
- [ ] With All types selected, the scored finding moves ahead of unscored candidates.
- [ ] JSON export contains all 12 findings and the original document.
- [ ] Optional revised-only audit returns zero candidates and eight Mention found states.

If counts differ, reload, leave the paste box empty, upload exactly one test file, and run again. A filtered screen can show fewer cards than the total candidate count. Markdown exports cap Top Risks at ten; use JSON when showing the complete set of twelve.

## What this demonstrates about viability

This is a functional acceptance fixture: it checks upload-to-report behavior, traceability, filtering, arithmetic, and sensitivity to recognized changes. It does not measure precision, recall, usefulness on unseen projects, user willingness to pay, or competition success. Those require independent project examples and reviewer labels.

Avoid claiming “AI automatically discovered every risk,” “zero findings means safe,” “the priority was calculated entirely from the document,” or “the app is deployed publicly.” The current version is rules-based, ratings are supplied by the reviewer, and the verified demonstration runs on localhost.
